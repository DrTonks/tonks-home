## 博客：不建议原样合入

远程提交将头像动画和图片优化捆绑在一起。主要阻断原因是实际可复现的图片优化缺陷，而不是凭动画观感断言性能严重恶化。

1. **Windows 优化清单的 URL 全部错误。** `scripts/optimized-images.mjs:55` 使用 `path.relative()` 拼 URL，没有把反斜杠转换为正斜杠。精确 Git 快照构建的 103 条 key 全部错误；`src/utils/optimized-image.ts:5` 查不到就返回原图。产物中 100 个原始 `/images/` 图片引用、0 个 `/_images/` 图片引用；165 个 WebP 仍然被打包。新增测试在 Windows 抛出 `thumbnailBytes` 读取 undefined，相关 5 项测试 4 通过、1 失败。
2. **合法 YAML 被误报为缺失图片。** `scripts/optimized-images.mjs:39–42` 用正则解析封面，`image: /images/projects/live.png # cover` 会把注释当文件名。应使用实际 YAML/frontmatter 解析。
3. **开发时图片更新失效。** manifest 只在 config setup 创建；替换原图后仍用旧 hash，刷新页面无效。修好 Windows key 后，这个问题会影响本地 `pnpm dev` 验收。需要文件监听和模块/清单失效。
4. **图片审计导出器不可用于删图决策。** `scripts/export-image-audit.mjs:45` 存在相同分隔符错误，漏报引用、CDN 和动态相册；第 10 行的项目外输出限制在 Windows 上可绕过。尚未据其结果删除任何源图片。

另外，生成器扫描三个目录的全部 PNG/JPEG，而不是仅扫描发布内容引用。完整映射也进入客户端 JS。现有 public 文件本来就会发布；没有证据证明这次新增泄露了真实隐藏照片，不能把相册的 hidden 标记当成访问控制。

## 动画实验方法

采用本机真实 Microsoft Edge headless、RTX 4060 Laptop GPU 的 ANGLE D3D11 WebGL；不是仅阅读源码，也没有强制软件 WebGL。旧版与远程版生产 dist 经本地静态服务提供。屏蔽第三方请求，固定随机数以保持横幅与贴纸一致，两版均走相同的本地资源回退。

- 桌面 1280×900、DPR 1；相同桌面 CPU 4 倍降速；移动视口 390×844、DPR 2。
- 每个场景使用 A→B→B→A 顺序，每次新建浏览器上下文并预热。
- 共 72 次按钮点击；每版每场景 8 次真实亮暗变化。系统/亮色同外观切换另外记录，不混入主表。
- 每次固定采样约 1.65 秒，记录 rAF 间隔、Long Task、头像 draw calls、主题释放/头像停止时间；测量窗口内不截图。
- rAF 间隔不是 GPU 实际呈现帧率；CPU 降速不是一台真实低端手机，也没有测 GPU 时间和耗电。此机器存在约 120 Hz 的刷新率上限。
- 初次 Windows tar 解包留下一个重复源图片，已逐文件对照 Git 归档 SHA 校正；初轮还与独立重建短暂重叠，因此初轮只作探索。精确快照最终轮没有并行构建，但开头 31 秒与正在结束的动画专项 Edge 夹具重叠，因此桌面统计只使用之后的第二组（每版 4 次真实变色）；CPU 降速与移动统计每版各 8 次，没有已知的其他测试重叠。

| 场景 | 旧版帧间隔 P95 | 新版帧间隔 P95 | 旧版最坏间隔 | 新版最坏间隔 |
|---|---:|---:|---:|---:|
| 常规桌面（每版 n=4） | 8.50 ms | 8.50 ms | 49.9 ms | 75.0 ms |
| 桌面 CPU 4 倍降速（每版 n=8） | 16.70 ms | 25.05 ms | 399.9 ms | 633.4 ms |
| 移动视口、头像离屏（每版 n=8） | 8.50 ms | 8.50 ms | 41.7 ms | 58.3 ms |

P95 列是每次切换的 P95 再取中位数；最坏间隔取所有纳入样本的最大值。它衡量调度，不直接等同渲染器实际呈现 FPS。

常规桌面持续帧间隔基本一致，旧版动作释放中位数约 631 ms；新版全页约 598 ms，但头像/互斥到约 1,156 ms 才完成，每次约 120 次头像绘制。静止和移动离屏不持续绘制。

压力测试有退化信号：逐次平均帧间隔的中位数由 13.67 ms 增至 16.81 ms，约 +23%；累计 >50 ms 帧间隔由 24 增至 31，Long Task 由 33 增至 44。新版其中一次出现约 633 ms 停顿，该时段没有已知其他测试进程重叠。两版本身均存在卡顿，首轮与最终轮幅度也有差异，因此不能把这些小样本提升为固定的性能损失百分比，更不能推出所有低端手机的帧率。新版将头像动画延续至全页 CSS 动画恢复之后，新增 CPU/GPU 竞争窗口，需要把可选效果与低负担默认体验区分。

独立专项夹具核对了两层共享 startTime 与几何换算，并检查 reduced-motion、无 WebGL、ready 拒绝、skip、取消、组件移除等路径；未确认新增 P1/P2 动画逻辑缺陷。夹具部分 finished 状态日志被自身未清除的超时后写覆盖，因此不以那些 timeout 文本判定产品超时。未覆盖所有真实硬件上下文丢失场景。

代码中两个圆形裁剪分别作用于整页 root 和头像/签名合成层，名义时长均 560 ms、同 easing、共享 startTime。它们不是两个完整页面各做一次扩散。新增的视觉内容还包括头像局部波浪与之后的 850 ms 粒子重组；界面主扩散结束后，头像仍继续，切换互斥也等待头像完成。这会让用户感觉动画拖长，即使大多数帧间隔相同。

移动视口头像在屏幕下方时，粒子绘制数为 0，但源码仍会提前创建 WebGL、纹理和缓冲，不能声称离屏完全零成本。桌面顶点缓冲约 384 KiB、两张纹理约 512 KiB，只是逻辑资源字节数，不是总显存实测。

## WebP 与原图保留

WebP 支持有损与无损；本次公共图片 q85、项目 q90、头像 q80 且缩至最长 512 px，使用的是有损方式。quality=85 不代表“保留 85% 信息”。依据：[Google WebP 说明](https://developers.google.com/speed/webp)、[sharp 输出选项](https://sharp.pixelplumbing.com/api-output/)。

对 7 张实际 display WebP 解码，与相同尺寸、EXIF 旋转后的源图进行 RGB 比较：节省 10.8%～88.9%，PSNR 37.09～40.65 dB，平均通道绝对误差约 0.60～2.02/255。另 1 张选择保留原 JPEG，不把其零误差说成 WebP 无损。全图指标不能证明中文细字、线条、透明边缘在放大后没有可见差异；还应人工验收这些局部。缩略图最长边 800 px，不能当原尺寸图使用。

11 个新增 CDN WebP URL 公开 GET 均为 200 且可解码；这部分路径变更本身成立。源码和 CDN 内容比对也通过。它与本地 `/_images` 的 Windows 清单问题是两条独立路径。

**现阶段不能删除部署目录里的全部原图。** sleepy 新接口返回稳定 `/images/...` 原图地址；旧链接、CDN 回退、动态 JSON、未纳入清单的图片、JSON-LD，以及转码不更小时的大小择优，都可能引用它们。源码原图也应保留，避免未来重复有损转码，并用于重新构建。

后续可以将编辑用原图与发布用图片区分：保留仓库/备份中的高质量原图，建立稳定旧 URL 到 WebP 的兼容映射，统一前后端消费契约，确认没有消费者依赖原文件后，只从 dist 清理确实未引用的副本。不能仅按扩展名批量删除 PNG/JPG，也不能直接把 sleepy 的 JSON 换成 `/_images/...`：当前后端校验只接受 `/images/`。

## sleepy 与主页的图片链路

```text
博客 public/data/projects.json、timeline.json
  → sleepy /blog-posts 读取最新条目
  → image/images 规范化为 https://blog.tonks.top/images/...
  → 主页 /api/blog-posts
  → ProjectCard 保留 HTTPS 地址，浏览器直接请求博客
```

- 主页 `src/api/blog.ts:65–69` 支持绝对 URL，`ProjectCard.vue:17–18` 取 image，所以主链路没有断。
- 当前 9 条项目、13 条时光机数据的非空图片引用均通过候选 URL 校验，实际博客目标图片可访问。
- 当前线上后端仍返回相对图片路径；时光机最新两张图不在旧 sleepy 本地副本中，images 数组为空。新后端能补齐 API 数组；**主页 TimelineCard 当前没有图片渲染，不代表拉取后卡片会自动出现图片。**
- 新旧 `/images/projects/` 入口改为 302，其他图片路径不受本次改动影响。当前兼容方案仍使用原图，主页不会自动获得新 `_images` WebP 的下载收益。
- 无需因为 HTTPS `<img>` 跨域显示去改 CORS；本次没有读取或修改云端 Apache 配置。公开 GET 只能证明检查时点的可访问性。

审查发现已存在的 `/images/projects/jxj.JPG` 在主页返回 200 图片，但候选原样 302 到博客同名路径时为 404；实际博客地址是小写 `jxj.jpg`。修复只对这一已知旧文件名添加显式映射，保留其他路径的大小写、校验、缓存头，不引入逐图网络探测。

另外，博客 base 配置为空或使用模板 example.com 时，新图片链接会失效；当前本地未设置这些覆盖，使用正确默认 HTTPS 地址。未读取生产私有配置，不能把本地配置结论当成线上配置验收；本次也未部署后端。
