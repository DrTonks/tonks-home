# 留言置顶、清理与表情扩展：初次调查记录

> 下文为首次本地改动时的历史记录。图片表情和懒清理现已完成并部署；当前状态与维护方法见 [运维说明](community-emojis-operations.md)。

## 已实现

- 桌宠天气移除数据源文字和链接。
- 主页：管理员点击消息的“审核”，可置顶或取消；群公告下展示置顶内容，聊天中仅增加置顶标记，仍按时间排列。
- 博客：管理员可直接置顶或取消，置顶留言及回复优先显示且不重复。
- 后端：`PATCH /blog/community/comments/<id>/pin`，使用现有管理员密钥，只接受布尔 `is_pinned`，只能置顶已发布留言。数据库初始化自动迁移。拒绝、删除、转为反馈会清除置顶。
- 首次滚动移到加载完成、DOM 更新后；最新消息窗口默认 300 条，额外补齐置顶及其可见父级。旧留言仍在数据库，但这不是完整的历史分页功能。

部署顺序：更新并重启 sleepy 后端，再发布主页和博客。本次仅修改本地代码，未发布。

## 软删除现状与清理建议

当前没有自动永久清理普通留言的任务。普通留言删除只改 `status`，没有 `deleted_at`，邮箱、正文等仍留在数据库；删除留言会连同后代一起标记。反馈主题有删除时间，且有消息、事件、来源快照、合并关系等关联数据。

转为反馈的普通留言同样会标记 `deleted`，但具有 `moved_to_feedback_id`，并被反馈来源表引用；这些属于有用途的数据，不能当垃圾直接删除。

建议后续实现独立维护命令：

1. 为普通留言增加删除时间，从明确删除操作时记录；历史记录删除时间未知，不按创建日期猜测。
2. 默认只预览候选数量和 ID；满足“已删除超过保留期、未转为反馈、没有任何保留数据引用”的整棵树才可永久清理。
3. 保留期可设 30 或 90 天；明确无需备份时，显式执行永久删除。先删依赖记录，再删主记录，事务执行。
4. 确认维护命令正确后，再接入服务器定时任务，记录清理计数。拒绝状态不自动视为已删除。
5. SQLite 删除后可重用空间；文件体积通常不会立刻缩小，需要时在维护时段执行 VACUUM。历史备份、日志中的数据由各自保留策略管理。

上述清理机制尚未实现或启用，本次没有删除任何真实数据。

## 示例表情系统

已读取用户指定仓库的 [Twikoo 组件](https://github.com/LeeHero0803/leehenry-blog/blob/main/src/components/misc/Twikoo.astro) 和 [OwO 清单](https://github.com/LeeHero0803/leehenry-blog/blob/main/public/emotion/owo.json)。前者初始化 Twikoo，并通过鼠标事件为评论图片实现三倍悬停放大；后者列出颜文字、Emoji、Azukisan、Bilibili、Blobcat、2233、Weibo、ALu 八组。实际运行时选用该清单的后台配置尚未核实。

我们当前两端是纯 Unicode 表情选择器，正文以安全纯文本显示。可以扩展成类似效果，无需迁移到 Twikoo：

- 两端使用同一份带版本号的表情清单，包含稳定标记、名称、分组、图片地址和尺寸。
- 编辑器插入如 `:2233:开心:` 的标记，后端仍存文本并走原有审核、长度限制。
- 渲染时仅识别清单内标记，输出固定图片；其他内容仍按文本转义，不开放任意 HTML。
- 主群聊、博客、回复引用和反馈来源快照使用一致解析规则；图片失效回退名称。
- 增加分组、搜索、最近使用和按需加载；图片优先放自有静态资源，素材来源与许可单独核实。

图片表情扩展尚未实施，这部分为本次调查结果和落地方案。
